📘 Guía de Skills y MCPs

Referencia práctica para usar las 7 skills del pipeline offline-first y los 8 servidores MCP que las potencian. Cada skill tiene triggers de activación, ejemplos de conversación y outputs esperados.

🧠 Skills del Stack

Escribe el trigger en OpenCode para activar la skill. Las skills auto-activadas no requieren trigger explícito.

🚀 prompt-inicial v2.0 orquestador

Orquesta el pipeline completo. Recibe 5 campos del usuario y dispara setup → spec → generación → validación en orden.

nuevo proyecto iniciar pipeline crear app iniciar flujo prompt-inicial
Tú: nuevo proyecto
// OpenCode te pide 5 campos:
📦 Nombre: ClinicaDentalPro
🎯 Tipo: Gestión de citas
💡 Descripción: App para recepcionistas...
🎨 Tono visual: 1-6
🔑 Módulos: dashboard, pacientes, citas
Output: Pipeline en marcha. Te guía paso a paso con pausas entre fases. Cada fase requiere confirmación explícita.

📦 setup-init v2.0 infraestructura

Valida entorno, crea estructura de carpetas, genera project.config.js y un script para descargar librerías locales.

iniciar setup crear estructura descargar libs verificar entorno setup descargar adicionales
Tú: iniciar setup
// Valida curl, permisos, crea carpetas:
→ Crea core/, modules/, assets/...
→ Genera descargar-libs.bat
→ Ejecuta el .bat (pide confirmación)
→ Si existe spec, descarga adicionales
Output: Estructura completa del proyecto + project.config.js + librerías en assets/.

📝 spec-creator v3.2 especificación

Transforma la historia de usuario en una spec técnica validada. Flujo interactivo: asunciones, preguntas 4+1 con barra de progreso, detección de librerías externas.

definir spec app nueva app completa crear especificación historia de app brainstorming app descubrir app diseñar app
Tú: definir spec app
// Responde asunciones una por una:
[🟩🟩🟨⬜⬜] ¿Multi-idioma? No
[🟩🟩🟩🟩⬜] ¿Modo oscuro? Sí
// Luego preguntas 4+1 con opciones
→ Genera specs/[app].md
Output: specs/[app].md con módulos, datos, librerías, reglas de negocio y validación.

🎨 design-ux-intelligence v2.5 diseño

Aplica principios de diseño profesional, paletas, tipografías, componentes Pines y WCAG AA. Se auto-activa cuando se menciona tono visual o diseño.

tono visual diseño distintivo UX profesional validar accesibilidad mejorar UI paleta de colores tipografía estilo UI
Tú: tono visual moderno y profesional
// Propone paletas + tipografías + estilo:
→ Paleta: #0F172A slate / #0D9488 teal
→ Tipografía: Inter + JetBrains Mono
→ Componentes Pines sugeridos
→ Checks WCAG AA automáticos
Output: Recomendaciones de estilo aplicadas inline. No genera código por sí sola — alimenta a code-generator.

⚙️ code-generator v2.3 generación

Genera código por fases: core primero, luego módulos uno a uno. Lee la spec y aplica estilo de design-ux. Pausas explícitas entre fases para evitar pérdida de contexto.

generar codigo crear módulos implementar spec build app escribir código
Tú: generar codigo
// Lee specs/[app].md y produce:
→ FASE A: index.html + core/*
→ ⏸️ Pausa, espera ✅ CORE OK
→ FASE B: Módulo 1...
→ ⏸️ Pausa, espera ✅ [modulo] OK
→ Cada bloque valida compliance automáticamente
Output: index.html + core/*.js + modules/[nombre]/*. Código listo para abrir con doble clic.

🛡️ stack-compliance-guard v2.3 validación

Guarda automática que se activa tras cada output de código. Bloquea imports ES6, CDNs, fetch y omisión de cifrado. Se puede invocar manualmente para auditar código existente.

validar stack comprobar reglas corregir imports verificar cifrado file:// compatible
Tú: validar stack
// Escanea código generado buscando violaciones:
→ ✅ Sin import/export
→ ✅ Sin type="module"
→ ❌ <script src="https://cdn..."> // BLOQUEADO
→ ✅ CryptoJS presente
→ Corrige automáticamente lo reparable
Output: Reporte de compliance. Correcciones automáticas aplicadas. Si hay ambigüedades, pregunta.

✅ validation-offline v2.4 testing

Validación final: análisis estático + guía DevTools + tests Playwright. Genera reporte técnico completo en docs/validacion-[app].md.

validar app verificar spec validar stack chequeo calidad reporte validación test automatizado playwright e2e
Tú: validar app
// Ejecuta 4 fases de validación:
→ Verificación estática (imports, CDNs, cifrado)
→ Guía DevTools (consola, storage, Lighthouse)
→ Tests Playwright (si están instalados)
→ Genera docs/validacion-[app].md
Output: docs/validacion-[app].md con resultados, screenshots y checklist de entrega.

🔌 Servidores MCP

8 MCPs configurados en opencode.json. Algunos los consumen las skills automáticamente, otros puedes invocarlos manualmente en conversación.

context7 remote

Resuelve documentación actualizada de librerías. Usado por setup-init y spec-creator para detectar URLs de descarga y versiones correctas.

// Uso automático (spec-creator):
→ Detecta libreriasAdicionales
→ Consulta context7: URL, version
// Uso manual en chat:
Tú: ¿Qué versión de Dexie usar?
→ OpenCode usa context7 internamente

excalidraw remote

Genera diagramas hand-drawn de arquitectura. Usado por spec-creator para ilustrar flujos de datos y estructura de módulos.

// spec-creator lo invoca automáticamente
→ Diagrama de arquitectura
→ Flujo de datos entre módulos
// Manual: Tú: haz un diagrama del flujo de 3 módulos

chrome-devtools local

Controla Chrome DevTools para debugging, captura de consola, screenshots y auditorías. Usado por validation-offline para validación dinámica.

// validation-offline lo usa para:
→ Tomar screenshot de la app
→ Revisar errores de consola
→ Auditar Lighthouse
// Manual: abre la consola y dime si hay errores

canva remote

Genera documentos visuales tipo doc, presentación o póster desde especificaciones. Uso opcional — no es core del pipeline.

// Manual, no se auto-activa en pipeline:
Tú: crea un póster con los resultados
→ Canva genera diseño en tu cuenta

filesystem local

Acceso a archivos del proyecto. Usado por todas las skills para leer/escribir specs, código, configs y reportes.

// Uso transparente — las skills lo usan automáticamente
→ Leer specs/[app].md
→ Escribir core/app.js
→ Guardar reporte en docs/

refero-styles local

Obtiene design.md de marcas reales (Linear, Stripe, Vercel, etc.) para inspirar paletas y estilos. Usado por design-ux-intelligence.

// design-ux lo activa automáticamente
→ Busca estilo: "dark minimal SaaS"
→ Obtiene paleta + tipografía + componentes
// Manual: busca un estilo oscuro minimalista tipo Linear

a11y local

Audita accesibilidad WCAG 2.2. Usado por validation-offline y design-ux para verificar contraste, ARIA, foco y etiquetas.

// validation-offline lo invoca así:
→ Audit URL: file:///.../index.html
→ Tags: wcag2a, wcag2aa, best-practice
→ Reporta violaciones con remediación

web-search local

Búsqueda web complementaria usando DuckDuckGo. Respaldo cuando context7 no tiene la librería o se necesita información general.

// Usado como fallback en setup-init
→ Si context7 falla, busca URL de librería en web
// Manual: busca "tailwind CSS v4 release date"

🎬 Escenarios de Uso

🚀 Escenario 1: Crear app desde cero

Pipeline completo: desde la idea hasta la app validada lista para entregar.

  1. Prompt inicial: escribe nuevo proyecto. Llena los 5 campos: nombre, tipo, descripción, tono visual, módulos.
  2. Setup: OpenCode ejecuta iniciar setup automáticamente. Crea carpetas, project.config.js, descarga librerías. Dale ✅ FASE 1 OK.
  3. Spec: definir spec app. Responde asunciones (barra de progreso) y preguntas 4+1. Se genera specs/[app].md. Dale ✅ FASE 2 OK.
  4. Diseño: design-ux se activa automáticamente si diste tono visual. Propone paleta, tipografía, componentes.
  5. Generación: generar codigo. Fase A: core + index.html. Pausa (✅ CORE OK). Fase B: módulos uno por uno. Cada bloque pasa compliance.
  6. Validación: validar app. Estático + DevTools + Playwright. Genera docs/validacion-[app].md.
Resultado: index.html que se abre con doble clic, 100% offline, sin CDNs, con spec y reporte de validación.

🛡️ Escenario 2: Corregir compliance en app existente

Tienes código de otro proyecto y quieres asegurarte de que cumple el stack offline-first.

  1. Abre OpenCode en la carpeta del proyecto existente.
  2. Escribe validar stack. La skill escanea todos los archivos buscando violaciones.
  3. Para cada violación: corrige automático si es posible (cambiar CDN a ruta local), o pregunta si es ambiguo.
  4. Al final muestra un resumen: bloqueados, corregidos, pendientes.
Tú: validar stack
→ Busca en **/*.html, **/*.js
→ 3 violaciones encontradas: 1 import, 2 CDNs
→ Corrigiendo... 2 CDNs → rutas relativas
→ Pregunta: El import es parte de una lib permitida?
Tú: No, elimínalo.
→ ✅ Stack compliant.

🎨 Escenario 3: Mejorar diseño y accesibilidad

Tu app funciona pero quieres darle un look más profesional y asegurar WCAG AA.

  1. Escribe mejorar UI o tono visual moderno. design-ux se activa.
  2. Propone paletas, tipografías, bordes, sombras y espaciado basados en marcas reales (vía refero-styles).
  3. Selecciona una propuesta. design-ux actualiza las variables CSS en project.config.js.
  4. Luego escribe validar accesibilidad. El MCP a11y audita contraste, ARIA, foco y etiquetas.
  5. Corrige los issues reportados (cambia colores de bajo contraste, añade roles ARIA, etiqueta inputs).

✅ Escenario 4: Validar app existente con reporte

Quieres un reporte profesional de la calidad de tu app antes de entregarla al cliente.

  1. Ejecuta validar app. validation-offline inicia su pipeline de 4 fases.
  2. Fase 1: Verificación estática — compliance guard chequea imports, CDNs, cifrado.
  3. Fase 2: Guía DevTools — te da comandos para revisar consola, Application tab, Lighthouse.
  4. Fase 3: Tests Playwright — si tienes Python, ejecuta python tests/test_app.py.
  5. Fase 4: Genera reporte completo en docs/validacion-[app].md con screenshots, resultados y checklist de entrega.
