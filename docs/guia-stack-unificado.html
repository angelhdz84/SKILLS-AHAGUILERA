Este documento analiza la evolucion de SKILLS-AHAGUILERA hacia un stack unificado que ofrece dos perfiles: Lite (el actual, file:// + Dexie) y Full (Bun + SQLite + .exe). El objetivo: mantener la simplicidad actual y anadir capacidades profesionales para vender mejor.

Parte 1 — Analisis

1.1 ¿Por que unificar?

Actualmente tienes SKILLS-AHAGUILERA (offline-first puro) y estabas considerando crear ATEJE-SKILLS (Bun + SQLite) como repositorio separado. Unificarlos en un solo stack con dos perfiles tiene estas ventajas:

👍 Ventajas de unificar

  • 0 skills duplicadas — spec-creator, daisyui-patterns, llm-wiki, ux-ui-universal son identicas en ambos stacks. Con repos separados tendrias que mantenerlas dos veces.
  • El stack actual no se rompe — El perfil Lite es exactamente SKILLS-AHAGUILERA hoy. Nadie pierde nada.
  • El perfil Full es un upgrade, no un reemplazo. El mismo code-generador elige plantillas distintas segun el perfil.
  • Deployment diferenciado: apps Lite van a GitHub Pages, apps Full se compilan a .exe. El orquestador sabe cual usar.
  • La Mini IA funciona en ambos perfiles: Transformers.js no requiere Bun.

👎 Riesgos a mitigar

  • Complejidad del code-generator — Al tener dos ramas de generacion, el SKILL.md se vuelve mas denso. Solucion: usar directorio templates/lite/ y templates/full/.
  • Confusion del usuario — "Lite" suena a inferior. Solucion: llamarlo perfil Web (abre con doble clic) y Desktop (compila a .exe).
  • Mantenimiento de dos ramas — Cada mejora a los templates debe aplicarse en ambos perfiles si aplica. Solucion: compartir logica comun (Alpine stores, UI helpers, routing) y solo diferenciar la capa de datos.
💡 Diferencia clave Los dos perfiles comparten el 80% del frontend (Alpine, DaisyUI, modulos, routing, UI helpers). Solo cambia la capa de datos (Dexie vs fetch API) y la existencia de un servidor. Esto hace que mantener ambos sea practico.

2.2 Cambios minimos 3 skills

Lite Full design-ux-intelligence

Que cambia:

  • Iconos: Bootstrap Icons sigue siendo compatible, pero el default pasa a ser Lucide (mas moderno, mejor percepcion profesional).
  • Animaciones: Animate.css solo se incluye en perfil Lite. En Full, las animaciones se manejan con Tailwind + CSS nativo (reduce peso).
  • Fuentes: En Full, las fuentes se sirven desde publico/fonts/ o system-ui. En Lite, se descargan a assets/fonts/ como hoy.

Impacto en el SKILL.md: Agregar al Paso 2 una nota: "Si perfil=Full, usa Lucide en lugar de Bootstrap Icons y omite Animate.css."

Ambos stack-compliance-guard

Que cambia:

  • Reglas nuevas para perfil Full:
    • Permite import/export en .ts del servidor (Bun los soporta nativamente).
    • Permite fetch('/api/...') en modulos frontend (rutas relativas al servidor Bun).
    • Verifica env.allowRemoteModels = false si se usa Transformers.js.
    • Verifica migraciones SQLite con WAL + foreign_keys.
  • Reglas que aplican en ambos perfiles: Sin CDNs, sin telemetria, cifrado de datos sensibles, espanol, UI DaisyUI.

Impacto en el SKILL.md: Agregar un bloque condicional "Si perfil=Full:" en el checklist de validacion.

Ambos ux-refactor

Que cambia:

  • La fase de auditoria debe detectar el perfil del proyecto (existe servidor.ts? hay package.json con bun? o solo index.html?).
  • Las recomendaciones de refactor se adaptan al perfil detectado.

Impacto en el SKILL.md: Agregar paso de deteccion de perfil al inicio de la Fase 1 (Auditoria).

Ambos prompt-inicial (Orquestador)

Lite Full code-generator

Que cambia: Es la skill con mayor impacto. El template de cada modulo cambia segun el perfil:

Template: Capa de datos (db.js)

Perfil Lite — db.js
// Lite: IndexedDB via Dexie
const db = new Dexie('AppDB');
db.version(1).stores({
  pacientes: '++id, nombre, email',
  citas: '++id, pacienteId, fecha'
});
window.db = db;

async function getAll(tabla) {
  return await db[tabla].toArray();
}
async function save(tabla, datos) {
  return await db[tabla].put(datos);
}
Perfil Full — db.js
// Full: fetch al servidor Bun
const API = '/api';

async function getAll(tabla) {
  const res = await fetch(`${API}/${tabla}`);
  return res.json();
}
async function save(tabla, datos) {
  const res = await fetch(`${API}/${tabla}`, {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify(datos)
  });
  return res.json();
}

// Fallback offline a Dexie
async function saveOffline(tabla, datos) {
  if (!navigator.onLine) {
    return await dbLocal[tabla].put(datos);
  }
  return save(tabla, datos);
}

Template: Modulo Alpine (module.js)

Perfil Lite — module.js
const Pacientes = {
  id: 'pacientes',
  titulo: 'Pacientes',
  icono: 'bi bi-people',

  async render() {
    // Datos directos de IndexedDB
    const items = await db.pacientes.toArray();
    return `...`; // HTML con Alpine
  },

  async guardar(datos) {
    datos.nombre = cryptoHelpers.encrypt(datos.nombre);
    await db.pacientes.put(datos);
    UI.toast('Guardado', 'success');
  }
};
Perfil Full — module.js
const Pacientes = {
  id: 'pacientes',
  titulo: 'Pacientes',
  icono: 'bi bi-people',

  async render() {
    // Datos via API Bun
    const res = await fetch('/api/pacientes');
    const items = await res.json();
    return `...`; // HTML con Alpine
  },

  async guardar(datos) {
    const res = await fetch('/api/pacientes', {
      method: 'POST',
      headers: {'Content-Type': 'application/json'},
      body: JSON.stringify(datos)
    });
    if (res.ok) UI.toast('Guardado', 'success');
  }
};
💡 Por que esto importa Nota que el HTML del modulo (module.html) es identico en ambos perfiles. Solo cambia la capa de datos. Esto significa que el 80% del codigo generado se reutiliza entre perfiles. Los templates de Alpine.js, DaisyUI, routing, UI helpers son los mismos.

2.4 Skills nuevas 2 nuevas

Nueva ateje-deployment-jigue

Proposito: Compilar y empaquetar la app Full a .exe portable.

Trigger: compilar app (solo disponible si perfil = Full)

Flujo:

=== ateje-deployment-jigue ===
1. Verifica que existe el proyecto Full
2. Compila CSS:   bunx tailwindcss --minify -i src/input.css -o publico/estilos.css
3. Compila .exe:  bun build ./servidor.ts --compile --outfile compilados/app.exe
4. Copia assets:  cp -r publico/* compilados/distribucion/
5. Comprime:      cd compilados && zip -r app-portable.zip distribucion/
6. Resultado:     compilados/app-portable.zip (~55 MB)

📦 Entregable final:
   app-portable.zip/
   ├── app.exe          (Bun runtime + codigo compilado)
   ├── estilos.css      (Tailwind + DaisyUI minificado)
   ├── index.html       (entry point HTML)
   └── bestiario/       (librerias JS estaticas)
⚠️ Atencion bun build --compile genera un binario de ~50 MB porque empaqueta el runtime Bun. Esto es normal. No requiere que el cliente instale Bun. El .exe es autocontenido. Alternativas mas ligeras (Neutralino 1-2 MB, Tauri 5-15 MB) requieren otros lenguajes (Rust).
Nueva ateje-ia-jutia Full Lite

Proposito: Anadir IA local (Transformers.js + ONNX) a cualquier app, independientemente del perfil.

Trigger: anadir ia (opcional, no se activa en pipeline base)

Que genera:

=== ateje-ia-jutia ===
1. Crea publico/workers/jutia-worker.js (Web Worker)
2. Anade Transformers.js al index.html:
   <script src="bestiario/transformers.min.js"></script>
3. Crea src/ia.js  (capa de IA con pipeline RAG)
4. Crea src/descargar-modelos.ts  (script de descarga unica)

Configuracion critica en el Worker:
   env.localModelPath = '/modelos/';
   env.allowRemoteModels = false;  // ❌ NUNCA true
💡 Diferencia clave A diferencia del perfil (Lite/Full), la IA es opcional en ambos. Puedes tener una app Full sin IA perfectamente funcional. La skill ia-jutia solo se activa si el usuario la pide explicitamente o si el orquestador detecta que la spec requiere procesamiento de lenguaje.

3.3 User Journeys

Para cada modulo, el flujo completo del usuario incluyendo caminos alternativos y errores.

Ejemplo: Journey "Registrar nuevo paciente" 
### Journey: Registrar nuevo paciente

**Actor:** Recepcionista
**Modulo:** Pacientes
**Precondicion:** Usuario autenticado en la app

**Flujo feliz:**
1. Usuario hace clic en "Nuevo paciente" (btn-primary en header)
2. Sistema abre modal/slide-over con formulario vacio
   Campos: nombre, email, telefono, fechaNacimiento
3. Usuario completa campos y hace clic en "Guardar" (btn-primary con loading)
4. Sistema valida en cliente:
   - nombre no vacio (min 2 caracteres)
   - email con formato valido
   - telefono: solo digitos, guiones y espacios
5. Sistema cifra nombre y email con cryptoHelpers.encrypt()
6. Sistema guarda en IndexedDB (Lite) o via API POST /api/pacientes (Full)
7. Sistema muestra toast "Paciente registrado correctamente" (duracion 3s)
8. Sistema cierra formulario y actualiza listado (el nuevo aparece primero)
9. ✅ Caso exitoso

**Flujo alternativo A: Email duplicado**
   - 5a. Sistema detecta email existente en BD
   - 6a. Muestra toast error "Ya existe un paciente con ese email"
   - 7a. Campo email marcado en rojo con mensaje "Email ya registrado"
   - 8a. No cierra formulario. Usuario corrige.

**Flujo alternativo B: Sin conexion (Full + Dexie fallback)**
   - 4a. navigator.onLine = false
   - 5a. Sistema muestra badge "Sin conexion — guardando localmente"
   - 6a. Guarda en IndexedDB local (cache)
   - 7a. Toast "Guardado localmente. Se sincronizara al reconectar"
   - 8a. Agenda sync cuando vuelva la conexion

**Flujo alternativo C: Error de validacion**
   - 3a. Usuario ingresa email invalido: "correo@"
   - 4a. Validacion en blur detecta email invalido
   - 5a. Campo email muestra error inline: "Ingrese un email valido"
   - 6a. Boton Guardar deshabilitado hasta corregir
   - 7a. Usuario corrige y reintenta → flujo feliz

**Postcondicion:** Paciente guardado en BD local. Listado actualizado.
⚠️ Atencion Los journeys son la seccion mas valiosa y la mas costosa de generar. El spec-creator debe detectar automaticamente los flujos alternativos tipicos: validacion fallida, duplicados, sin conexion, datos vacios. No preguntar cada uno al usuario.

3.5 Testing Criteria

Checklist de pruebas manuales y automatizables que deben pasar antes de entregar.

## Testing y Criterios de Aceptacion

### Tests manuales (QA)
- [ ] Crear paciente con datos validos → aparece en listado inmediatamente
- [ ] Crear paciente con email invalido → muestra error "Email no valido"
- [ ] Buscar paciente por nombre parcial → resultados filtrados en tiempo real
- [ ] Eliminar paciente → confirmacion modal → desaparece del listado
- [ ] Editar paciente → cambios reflejados en listado y detalle
- [ ] Sin conexion (desactivar WiFi) → badge "offline" visible + datos guardan local
- [ ] Volver a conectar → badge cambia a "online" sin errores
- [ ] Exportar a PDF → archivo se descarga con datos visibles
- [ ] Modo oscuro → toggle funciona, persiste al recargar

### Tests automatizables (Playwright)
- [ ] Carga inicial: 0 errores en consola, librerias globales presentes
- [ ] CRUD completo: crear, leer, actualizar, eliminar paciente
- [ ] Busqueda: input de busqueda filtra tabla en < 200ms
- [ ] Exportacion: clic en exportar genera archivo (verificar tipo MIME)
- [ ] Responsive: viewport 320px sin scroll horizontal
- [ ] Accesibilidad: botones icon-only tienen aria-label
- [ ] Tema oscuro: clases CSS cambian correctamente

### Criterios de aceptacion (Gherkin)
Escenario: Recepcionista registra nuevo paciente
  Dado que el recepcionista esta en el modulo Pacientes
  Cuando hace clic en "Nuevo paciente"
  Y completa el formulario con datos validos
  Y hace clic en "Guardar"
  Entonces el sistema guarda el paciente en la base de datos
  Y muestra un toast de confirmacion
  Y el paciente aparece en el listado

Escenario: Recepcionista busca paciente
  Dado que hay 10+ pacientes registrados
  Cuando escribe "Maria" en el campo de busqueda
  Entonces la tabla muestra solo pacientes con "Maria" en nombre o email
  Y la busqueda se actualiza en menos de 200ms

3.6 Asunciones 4+1 — Comparacion

Las asunciones actuales son muy tecnicas. Las nuevas mezclan negocio con UX:

#Asuncion actualAsuncion propuestaMejora
1 Arquitectura SPA hash-based Flujo principal: ¿El usuario sigue una secuencia fija (A→B→C) o salta entre modulos libremente? Define si el router necesita wizard/steps o navegacion libre
2 IndexedDB via Dexie, sin JOINs Datos concretos: ¿Que entidades maneja la app? ¿Que campos tiene cada una? (¿Quieres repasarlas una por una?) Obtiene el esquema exacto antes de generar codigo
3 Clave cifrado en localStorage Pantallas clave: ¿Cuales son las 3-4 pantallas principales? ¿Que ve el usuario en cada estado (vacio, carga, error)? Cubre los 3 estados (empty, loading, error) desde la spec
4 Mobile-first, modo oscuro claro Reglas de negocio: ¿Hay calculos, validaciones, logicas especificas del dominio? (ej: "no agendar citas en feriados", "maximo 3 cuotas") Captura reglas de dominio que el generador no puede adivinar
5 Modulos activables en config Contenido/copy: ¿Textos especificos para botones, mensajes, ayuda? (¿O prefieres genericos y luego personalizar?) Evita nombres genericos ("Guardar", "Cancelar") cuando el dominio tiene vocabulario propio
💡 Por que cambiar las asunciones Las asunciones actuales son decisiones tecnicas que el usuario no deberia tener que validar ("Arquitectura SPA hash-based"). Las nuevas asunciones son sobre el negocio y la experiencia de usuario — cosas que solo el usuario conoce y que el agente no puede adivinar. El refinamiento 4+1 se vuelve asi mas util y menos tecnico.

Personalizacion profesional

  • Icono de aplicacion: .ico integrado en el .exe. El logo del cliente en el escritorio.
  • Ventana sin bordes: Sin barra de direcciones, sin botones de navegador. Parece nativo.

  • Nombre del proceso: Aparece como "ClinicaPro.exe" no como "bun.exe" o "node.exe".

Proteccion del codigo

El .html se entrega con codigo fuente visible. El .exe de Bun se entrega compilado (no es ofuscacion total, pero requiere ingenieria inversa avanzada). Para proteccion adicional:

  • Minificar codigo antes de compilar
  • Ofuscadores JS (javascript-obfuscator) antes del build
  • Archivo de licencia .key firmado con Web Crypto

6.3 FAQ

¿Si elijo Lite, puedo migrar a Full despues?

Si, y es el camino recomendado. Los modulos Alpine.js son identicos. Solo cambia la capa de datos (db.js) y la existencia de un servidor. Puedes empezar en Lite, desarrollar toda la funcionalidad, y cuando estes listo para entregar, activar el perfil Full para generar el servidor y compilar a .exe.

¿Pesa mucho el .exe de Bun?

~50-55 MB. Bun empaqueta su runtime en el binario. Esto significa que el cliente NO necesita instalar Bun, Node.js ni nada. El .exe es autocontenido. Es comparable al peso de cualquier app desktop moderna. Si 50 MB es demasiado, evaluar Neutralino.js (~2 MB) o Tauri (~10 MB).

¿La Mini IA funciona en el perfil Lite?

Si. Transformers.js funciona en el navegador, no requiere Bun. Los modelos se descargan una vez (~150 MB) y se cachean. La unica diferencia entre Lite y Full es que en Full puedes usar el Worker de Bun en lugar del Web Worker del navegador.

¿Que pasa con las apps existentes creadas con SKILLS-AHAGUILERA?

Siguen funcionando exactamente igual. El perfil Lite es SKILLS-AHAGUILERA sin cambios. El stack unificado solo anade opciones, no modifica el comportamiento existente.

¿Merezco mantener dos ramas de templates en code-generator?

No es tan grave como parece. Los templates comparten ~80% del codigo (Alpine stores, UI helpers, routing, modulos HTML). Solo la capa de datos (db.js) y el entry point (index.html vs servidor.ts) son diferentes. Puedes tener un template base compartido y solo templated diferenciados para esas piezas.

¿Puedo personalizar el icono del .exe?

Si. Bun soporta --icon en bun build --compile para Windows (.ico) y macOS (.icns). Tambien puedes embeber metadatos (version, descripcion, compania) con --metadata.

¿Que licencia tienen los modelos ONNX de la Mini IA?

Todos los modelos mencionados son Apache-2.0 (Transformers.js, all-MiniLM-L6-v2, distilbert, bert-spanish). No hay restricciones de uso comercial.

Parte 7 — Conclusion

Resumen ejecutivo

  • No crees ATEJE-SKILLS como repo separado. Evoluciona SKILLS-AHAGUILERA anadiendo un selector de perfil al inicio.
  • 4 skills no cambian, 3 requieren cambios minimos, 3 requieren cambios significativos, 2 son nuevas.
  • El 80% del codigo (Alpine, DaisyUI, modulos, routing) se comparte entre perfiles. Solo la capa de datos cambia.
  • Las specs mejoradas (Modelo Datos, Journeys, Wireframes, Testing) elevan la calidad sin alargar el proceso.
  • La Mini IA es opcional y funciona en ambos perfiles. Empezar solo con FlexSearch (7 KB, sin modelos).
  • La entrega en .exe via Bun --compile pesa ~55 MB pero no requiere runtime externo y protege el codigo.
🎯 Voto final Unificar en un solo stack con perfiles (Web/Desktop). La alternativa de dos repos separados duplica mantenimiento sin beneficio real. El stack actual no se rompe, solo se expande.
